# ⚖ 校驗關卡 · 模組完整性


## 核心原則

```
模組 = 程式碼 + README.md + DESIGN.md
缺一不可，殘缺即異端
```

## 自動掃描

執行掃描指令碼（跨平臺）：

```bash
# 在 verify-module 目錄下執行（推薦）
node scripts/module_scanner.js <模組路徑>
node scripts/module_scanner.js <模組路徑> -v      # 詳細模式
node scripts/module_scanner.js <模組路徑> --json  # JSON 輸出
```

## 校驗標準

一個完整的模組必須包含：

```
module/
├── README.md      # 必須 - 模組是什麼、為什麼存在
├── DESIGN.md      # 必須 - 設計決策、權衡取捨
├── src/           # 程式碼實現
└── tests/         # 測試用例（如適用）
```

## 檢測項

### 必須存在

| 檔案 | 說明 | 缺失後果 |
|------|------|----------|
| `README.md` | 模組說明文件 | 🔴 阻斷交付 |
| `DESIGN.md` | 設計決策文件 | 🔴 阻斷交付 |

### 推薦存在

| 檔案/目錄 | 說明 | 缺失後果 |
|-----------|------|----------|
| `tests/` | 測試目錄 | 🟠 警告 |
| `__init__.py` | Python 包標識 | 🟡 提示 |
| `.gitignore` | Git 忽略配置 | 🔵 資訊 |

### README.md 必須包含

- [ ] **模組名稱與定位** — 一句話說明是什麼
- [ ] **存在理由** — 為什麼需要這個模組
- [ ] **核心職責** — 做什麼、不做什麼
- [ ] **依賴關係** — 依賴誰、被誰依賴
- [ ] **快速使用** — 最簡示例

### DESIGN.md 必須包含

- [ ] **設計目標** — 要解決什麼問題
- [ ] **方案選擇** — 考慮過哪些方案、為何選當前方案
- [ ] **關鍵決策** — 重要的技術決策及理由
- [ ] **已知限制** — 當前方案的侷限性
- [ ] **變更歷史** — 重大變更記錄

## 自動觸發時機

| 場景 | 觸發條件 |
|------|----------|
| 新建模組 | 模組建立完成時 |
| 模組重構 | 重構完成時 |
| 提交前 | 程式碼提交前檢查 |

## 校驗流程

```
1. 執行 module_scanner.js 自動掃描
2. 檢查檔案結構是否完整
3. 檢查 README.md 各項是否齊全
4. 檢查 DESIGN.md 各項是否齊全
5. 檢查程式碼與文件描述是否一致
6. 輸出校驗報告
```

## 校驗報告格式

```
## 模組校驗報告

### 模組: <模組名>

✓ 透過 | ✗ 未透過

### 檔案檢查
- README.md: ✓ 存在 / ✗ 缺失
- DESIGN.md: ✓ 存在 / ✗ 缺失
- tests/: ✓ 存在 / ⚠️ 缺失

### 內容檢查
- README 完整性: ✓ 完整 / ⚠️ 缺少 [X, Y, Z]
- DESIGN 完整性: ✓ 完整 / ⚠️ 缺少 [X, Y, Z]

### 結論
可交付 / 需補充後交付
```

## 快速修復

如果缺少文件，可使用文件生成器：

```bash
/gen-docs <模組路徑>
```
